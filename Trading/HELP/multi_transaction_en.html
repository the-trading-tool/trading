Multi-Strategies premium/multi_transaction.pyPremium

Manages and simulates several trading strategies in parallel, each with its own index universe, buy/sell conditions and budget. It forms the basis for the KPIs on the dashboard page and for automated trading.

Premium feature (Sidebar → Portfolio → Multi-Strategies), visible only to admin accounts with the license feature strategy_engine.

Structure of a strategy

Strategies are stored in config.db under the key multi_transactions as a nested structure:

  • Outer level: strategy name (e.g. "Value Trend Strategy", "Support/Resistance Strategy")
  • Inner level: index name (e.g. SPX, GDAXI, MDAXI) each with:
FieldMeaning
buyBuy condition as an expression over indicator columns, e.g. overallValueTrend > 65
sellSell condition, e.g. ewo < ewo_ema
num_assetsMaximum number of simultaneously held names for this index
investStarting capital for this index (in currency or the system currency)
currencySettlement currency; ANY = no conversion
order_bySort column for selecting the top names (e.g. sortino, overallValueTrend)
stop_loss optionalHard stop-loss in % for this index only; overrides the global stop_loss_pct from Settings. Sells once the daily low touches entry × (1 − %/100) (0 = off). Covers positions that would otherwise never get a sell signal.
trailing_stop optionalTrailing stop in % below the highest close since entry (moves up with the price; 0 = off).
require_isin optionalRestricts this index to names with a valid ISIN; overrides the global switch.
signal_window optionalCarry-over window in bars for multi-line buy/sell formulas: one condition per line, each may have been met within that many bars. 1 = all on the same bar (previous behaviour). Overrides the global "Signal window" setting.
Example: 'buy': '(close <= sup_support*1.015) & (rsi < 40) (ewo > ewo_ema)', 'signal_window': 5

Usage

  • Data from: select the simulation year (current year or archive DBs asset_simulation_{year}.db)
  • Filter "buy/sell computation from date": limits the simulated trades to a period (default: last Friday)
  • Compute transactions: starts the simulation for all strategies × indices – may take a while depending on the data volume (progress bar)
  • Reset: discards the computed results again
  • Show transaction detail trend & data: shows a detail view per index with metrics, a trade table and a price chart
Result cache: after computing, the result is cached (keyed on strategy config, year, date, currency). An Excel download or other UI interactions then no longer trigger an expensive recompute – a "Cached result" note is shown. A real recompute only starts via "Compute transactions" or when an input (config/year/date/currency) changes.
A name is never held twice at the same time: if an earlier-processed strategy/index already holds a ticker, buy signals for the same ticker in a later strategy/index are ignored on the overlapping days (time-aware, prevents duplicate positions across strategies AND indices). Sequential re-buys after a sell remain allowed; the order in the config decides who gets the name.
Data-quality check: After computing, traded tickers with inconsistent OHLC (daily close outside [Low, High]) are flagged as potential data errors — typically an unadjusted split (close ~6× High) or pence/pounds on .L names (~100×). The simulator skips such bars (otherwise phantom trades arise, e.g. −83% from buying at the wrong price + the hard stop firing against the correct low). Hits are stored in data_quality.db; a warning block shows the cause and cleanup commands. Note: re-fetching only helps if the data provider now returns correct values — a genuine upstream error needs a manual override.

Analysis

  • Cumulative-gain chart per index: development of the cumulative profit across all simulated trades
  • Trade table with Excel export (📥 download trades/buys/sells)
  • Monthly performance heatmap (month × year, RdYlGn colour scale)
  • Strategy metrics: open positions, profit factor, hit rate, avg. profit/trade, realised profit, longest winning/losing streak, best/worst trades (3 months & 1 year)
  • Portfolio overlap warning: reports if the same ticker is held in several strategies at once
  • Market context per buy recommendation (columns "Market trend" and "Market season") — see below

Market context of the buy recommendations

The buy table carries two columns describing the state of the row's own index (column "Index") on the buy date. Both are computed from that index's local daily series (tradinglib/market_phase.py).

ColumnMeaning
Market trend ↑ Uptrend = index above its 200-day average and that average rising · ↓ Downtrend = below and falling · → Transition = turned but unconfirmed (above a falling average, or below a rising one).
Market season Share of earlier years in which this index rose over the next 21 trading days from this point in the year. Arrow from 60 % (↑) and up to 40 % (↓).

Computed causally: only data up to the buy date enters, and the seasonal figure uses only years before the trade's year. The value beside an old trade is therefore one that was knowable that day — otherwise the marker could not be measured honestly against the outcomes.

Context, not a quality mark. Measured over 4372 closed trades (buy years 2020–2022, 2025–2026) neither column separates winners from losers:
  • Season: "strong" 54.0 % hit rate / avg +2.57 % against "weak" 53.2 % / +2.55 %. Correlation between up-probability and outcome: +0.018.
  • Trend: pooled, "uptrend" looks better (avg +2.96 % vs +2.69 %), but that is a composition effect: 2021 produced 852 uptrend trades and zero downtrend ones, 2022 the reverse. Within every year holding both groups, "downtrend" did better (+1.94 pp on average, 3 of 3 years) — consistent with strategies that deliberately buy weakness.
The columns are therefore meant as context and deliberately not colour-coded. As a filter, the index trend criterion was already tested and rejected (−33 % return).
"–" instead of a seasonal figure means too little local history; at least four years are needed. Currently affected are ^RUT and ^IBEX (2 years each) — deepen those series with python get_asset_data.py /tickers:^RUT,^IBEX 1d:max.
Valuation of open positions in the summary: "Total value (open at cost)" values still-open positions at the buy price (≈ realized P&L only). In addition, "Unrealized P&L (open positions)" (valuation at the current/last price minus entry) and "Total value incl. unrealized" are shown — the latter matches the "Portfolio value today" metric on the Dashboard (small differences due to price/valuation timing are possible).
For strategies whose name contains "value trend", a ⚠️ geopolitics notice is additionally shown automatically.

Relationship to other pages

  • Dashboard: shows a summary of all strategies (starting capital, portfolio value, performance, max. positions)
  • Paper / Live Trading: strategies configured here can be selected there under "Enable strategies" for automatic order execution
  • asset_perf2.py calls run_notifier() after each run, which reports new buy/sell signals of these strategies via Pushover (see the "Signal notification" help)
